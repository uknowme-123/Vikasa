# Firebase Realtime Database Setup

Firebase is an optional storage backend for the Vikāsa Flask API. No Firebase project, database, or credentials are included in this repository.

## Configuration

Set the following environment variables when `STORAGE_BACKEND=firebase`:

```text
STORAGE_BACKEND=firebase
FIREBASE_PROJECT_ID=your-project-id
FIREBASE_DATABASE_URL=https://your-project-id-default-rtdb.firebaseio.com/
FIREBASE_CREDENTIALS_PATH=C:\secure\firebase\service-account.json
FIREBASE_TIMEOUT_SECONDS=10
```

`FIREBASE_CREDENTIALS_PATH` may be omitted when the runtime provides Application Default Credentials. The path must point to a protected file outside the repository. Never commit the service-account JSON or copy private keys into `.env.example`.

For local development without Firebase, keep `STORAGE_BACKEND=memory`. The in-memory backend remains the default and is used by unit tests.

## Database structure

Sensor readings are stored at:

```text
/readings/{reading_id}
```

Each reading contains the validated sensor payload plus a server-generated `created_at` timestamp. The stable client-supplied `reading_id` is the canonical lookup key and is validated against `READING_ID_PATTERN`.

The structure supports:

- Direct lookup by reading ID: `/readings/{reading_id}`
- Plant filtering: query `plant_id`
- Session filtering: query `session_id` (combined with other filters locally)
- Time ordering and range filtering: `timestamp`
- Paginated API responses: sorted and sliced by timestamp after retrieval

Firebase can efficiently order/filter by one child at a time. The service therefore uses a plant query when available and applies session and time filters locally. For large datasets, a future indexed materialized view may be needed.

## Duplicate-write strategy

The service uses a Firebase transaction at `/readings/{reading_id}`. The transaction only writes when that key is absent; an existing key raises a duplicate error. This makes retries with the same reading ID safe and avoids replacing an existing record.

Reading IDs should be generated by the acquisition layer with a collision-resistant scheme, for example a device/session prefix plus a UUID or monotonic device sequence. The exact device-side format remains a pending decision; the backend only enforces the configured pattern.

## Database rules and indexes

The following is a starting point for a project-owned Realtime Database rules file. It is not applied automatically and must be reviewed with the team's authentication model:

```json
{
  "rules": {
    "readings": {
      ".read": "auth != null",
      ".write": "auth != null",
      ".indexOn": ["plant_id", "session_id", "timestamp"]
    }
  }
}
```

Do not use permissive public read/write rules in a deployed database. Device authentication, user roles, and least-privilege access are pending decisions.

## Local execution

1. Install dependencies from `requirements.txt` only after reviewing the project dependency policy.
2. Copy `.env.example` to a local `.env` file, or export variables through the process environment.
3. Use `STORAGE_BACKEND=memory` for local API development without Firebase.
4. Use `STORAGE_BACKEND=firebase` only with a real Firebase project, valid database URL, and protected credentials.
5. Start the Flask application through the repository's chosen application entry point.

The API must return a storage error when Firebase initialization, authentication, network access, timeout, or database operations fail. It must not return a successful write response unless the Admin SDK confirms the transaction completed.

## Verification status

This repository contains the Firebase integration code and mocked tests only. No production Firebase project has been configured or tested here, and no sensor readings are seeded.
